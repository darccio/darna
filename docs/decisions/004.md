# Commit and patch-set verification for quality guardrails

Darna checks that a commit is complete (ADR-000) and cohesive (ADR-003). Darna does not check that a commit works. CLAUDE.md defines an atomic commit as one that compiles, passes tests, and is independently reviewable. Darna proves the first and third properties. It does not prove the second. **This ADR adds opt-in verification: darna MAY run one user-specified command against a materialized git tree and report pass or fail.**

Issue #5 asks how pre-commit quality guardrails fit darna's loop model. This ADR answers that question and sets the rules for a future implementation. This ADR does not implement the feature.

## 1. Terms

This ADR uses RFC 2119 keywords (MUST, MUST NOT, SHOULD, SHOULD NOT, MAY) for binding design rules.

- **Worktree**: the files on disk, tracked and untracked.
- **Index**: the git staging area.
- **Tree**: a git tree object. A tree is the content that one commit would contain.
- **Materialize**: to turn a tree into files on disk, so a command can run against it.
- **Patch set**: a sequence of commits between a base and HEAD, per CLAUDE.md's atomic-commit workflow.

## 2. Why the worktree is not enough

A pre-commit hook that runs `go test` against the worktree checks one thing: is the worktree green. This is useful. It is not sufficient.

The worktree is the one tree that never enters git history. Once a user stages files progressively, no single commit's content equals the full worktree. Verifying the worktree proves a tree nobody will ever check out.

This gap is not hypothetical. Four concrete cases pass a worktree check and fail the commit they produce:

1. **Partial staging.** `git add -p` puts content in the index that exists nowhere on disk. Darna's own static check already handles this for analysis, via an overlay that reads staged content with `git show :path` ([validator.go:109](../../internal/validator/validator.go:109)).
2. **Staged deletions.** `git.GetStagedFiles` filters with `--diff-filter=ACMR` ([git.go:16](../../internal/git/git.go:16)), which excludes deletions. A commit that deletes a file still referenced elsewhere passes both the worktree check and darna's static check.
3. **Untracked build inputs.** `go.mod`, `go.sum`, or a `//go:embed` source can be untracked. The worktree sees them. The commit tree does not.
4. **Non-Go files.** Darna's static check inspects `.go` files only (ADR-003, Negative consequences). A worktree test run may pass while a staged config file breaks the build.

**Rule V1**: A worktree check MUST NOT be presented as proof that a commit is correct. It proves only that the worktree is correct.

## 3. Verification tiers

Darna SHOULD offer three verification tiers. Each tier answers a different question. Each tier is more expensive than the last.

| Tier | Flag value | Question it answers | Cost |
|---|---|---|---|
| Worktree | `--verify=worktree` | Is the worktree green? | One run, no materialization |
| Index | `--verify=index` | Is the commit-to-be green? | One run, one materialized tree |
| Range | `--verify=range=<rev>` | Is every commit in the patch set green? | N runs, one worktree setup |

**Rule V2**: All three tiers MUST be off by default. Verification is opt-in, like every existing darna flag (`--committable`, `--single-changeset`, `--commit-msg`).

**Rule V3**: The index and range tiers MUST verify a materialized tree, not the worktree. Materialization for a single tree is:

```
tree   = git write-tree
commit = git commit-tree <tree> -p HEAD -m verify
         git worktree add --detach <tmpdir> <commit>
```

`git write-tree` turns the index into a tree object. `git commit-tree` wraps the tree in a dangling commit, so `git worktree add` has a commit-ish to check out. `git worktree add` alone does not accept a tree object.

**Rule V4**: Materialization MUST NOT use `git stash create`. A stash snapshots the worktree and the index together. This reintroduces worktree contamination, which V3 exists to remove.

**Rule V5**: The range tier answers a question about the whole patch set, not a single commit. It SHOULD run at pre-push, not pre-commit. Rewriting history during interactive rebase invalidates any per-commit result computed before the rewrite; verifying at push time avoids re-running on every rebase step.

## 4. Execution model

**Rule E1**: Darna MUST run exactly one command per verification target. Darna MUST NOT implement a task graph, a task list, parallel task execution, or file-glob matching.

**Rule E2**: Darna MUST run the command through a shell (`sh -c`), not as a raw argument vector. Users chain commands (`make lint && make test`); a shell is required for that syntax.

**Rule E3**: If a user wants multiple checks, the user SHOULD compose them in one command, for example `make check`. Darna's own Makefile already defines `all: lint test build` as this kind of composite target.

This ADR rejects a prove_it-style task runner (multiple named tasks, each with its own type, schedule, and cache). prove_it needs that machinery because JavaScript has no content-addressed build cache; its task cache and churn-tracking refs exist to work around that gap. Go already has a content-addressed test and build cache. A second cache layer on top of it would be redundant and would grow darna toward becoming a task runner. Rule E1 exists to prevent that growth.

## 5. Configuration

ADR-000 states: "The tool requires no configuration files." This ADR amends that statement.

**Rule C1**: Darna MUST accept verification settings from an optional `.darna.json` file in the repository root. The file MUST use JSON, not YAML or another format, so that no new dependency is added (darna's only current dependency is `golang.org/x/tools`; the standard library's `encoding/json` covers this).

**Rule C2**: The config file MUST contain at most a `verify` section, holding a `command` string and a `timeout` duration string:

```json
{
  "verify": {
    "command": "make check",
    "timeout": "10m"
  }
}
```

**Rule C3**: Command-line flags MUST override config file values when both are present. This mirrors the existing `--commit-msg` / `--prompt-file` pattern: a named default, overridable per invocation.

The flags are `--verify=<scope>`, `--verify-cmd=<command>`, and `--verify-timeout=<duration>`. `--verify-cmd` and `--verify-timeout` are valid only when `--verify` is set, matching the existing guard on `--prompt-file` requiring `--commit-msg` ([main.go:45-48](../../cmd/darna/main.go:45)).

ADR-000's no-configuration claim was already softened once, by `--prompt-file` (ADR-002), which reads a user-supplied file. This ADR states the amendment directly instead of leaving it implicit: darna MAY read a small, single-purpose config file. Darna MUST NOT grow that file into a general task or plugin configuration format.

## 6. Who is gated

**Rule G1**: Verification MUST behave identically for human and agent commits. Darna MUST NOT detect the caller's identity (for example, via an agent-specific environment variable) and skip verification for one group.

prove_it skips verification unless `CLAUDECODE` is set in the environment; human commits pass through unchecked. Darna rejects this pattern for three reasons:

1. It splits commit history into proven and unproven halves. Darna exists to keep `git bisect` reliable across the whole history, not half of it.
2. Identity detection does not generalize. Darna already supports four external agents ([agent.go:52](../../internal/agent/agent.go:52)); each may set different environment variables, or none.
3. It is an unaudited, silent form of `--no-verify`. A human already has `--no-verify` for that purpose, and it is visible in the commit's reflog context.

A user who wants agent-only enforcement MAY add that check in their own hook script. Darna MUST NOT implement it.

## 7. Result cache

Verification cost is what makes G1 acceptable. Darna SHOULD cache passing results, keyed by tree content, so a repeated commit of the same tree does not re-run the command.

**Rule R1**: The cache key MUST be `sha256(treeSHA + verifyCommand + toolchainVersion)`. The tree SHA identifies the content. The command and toolchain version are part of the key because a different command or toolchain can produce a different result for the same tree.

**Rule R2**: The cache MUST store passing results only. A failing result MUST NOT be cached. A failing check MUST re-run on every invocation until it passes.

**Rule R3**: The cache MUST live at `.git/darna/verified`, inside the repository's own `.git` directory. This location is per-clone and is never pushed, fetched, or merged.

**Rule R4**: The cache is a performance optimization. It MUST NOT be presented as an attestation that a commit is verified. A durable, shareable attestation is a separate concern, served by CI and a signed status check, not by this cache.

### 7.1 Rejected: git notes and commit trailers

A commit trailer is part of a commit's content. Changing it changes the commit's SHA. A trailer therefore cannot attest to the commit that contains it — the attestation and the content it describes cannot both be fixed at once.

Git notes avoid that specific problem, since notes are stored outside the commit object. They fail for a different reason: CLAUDE.md requires "heavy use of interactive rebase to restructure, reorder, squash, or split commits." Rebase creates new commit SHAs. A note keyed to the old SHA becomes orphaned, or worse, appears attached to an unrelated new commit that reused a note ref by coincidence. A cache with a near-total invalidation rate on every rebase is worse than no cache.

**Rule R5**: Darna MUST NOT write git notes or commit trailers as a verification record.

## 8. Disclosed writes

ADR-001 and ADR-002 reject auto-staging and auto-committing: darna outputs information and does not modify repository state. This ADR narrows, not breaks, that rule.

**Rule W1**: Darna MAY write the following, and MUST NOT write anything else:
- Unreferenced git objects, created by `write-tree` and `commit-tree` (Rule V3). These objects are not attached to any ref. They are garbage-collectible by normal git garbage collection.
- A temporary worktree, created by `git worktree add` and removed before the command returns.
- The cache file at `.git/darna/verified` (Rule R3).

**Rule W2**: Darna MUST NOT write to any ref, MUST NOT modify the index, and MUST NOT modify a tracked file in the user's worktree.

W1's writes go into `.git/`, the directory git tools already use for local state (`.git/hooks`, `.git/COMMIT_EDITMSG`, `.git/rebase-merge`). They do not change what `git status`, `git log`, or `git diff` report. This is a materially different class of write than the auto-stage and auto-commit proposals that ADR-001 and ADR-002 rejected, both of which would have changed user-visible repository state.

## 9. Dispatch order

A future implementation SHOULD run gates in ascending cost order: atomicity, then cohesion, then verification. ADR-003 already establishes this order for cohesion, running it only after atomicity passes, to avoid computing a second, more expensive check on a commit that is already known to fail. Verification is the most expensive of the three gates and SHOULD run last, for the same reason.

`--committable` and `--commit-msg` currently exit before validation runs at all ([main.go:34-63](../../cmd/darna/main.go:34)). A future implementation MUST reject combining `--verify` with either flag, rather than silently ignoring it.

## 10. Security disclosure

The index and range tiers run a command inside a tree built from the code under test. That code may include an untrusted `Makefile` target or an untrusted Go test. This is the same class of risk CI already accepts, run in the same environment as everything else on the user's machine, not a CI sandbox. A future implementation MUST document this in user-facing help text, not only in this ADR.

## 11. Alternatives considered

**Coordinate only; do not execute.** Darna would emit a list of trees to verify; an external runner (lefthook, prove_it) would execute checks. Rejected: this removes the one thing no existing runner does — materializing an index tree via `write-tree`/`commit-tree` (Rule V3). Without execution, the feature reduces to "install a task runner," which the issue could already do without darna's involvement.

**Full config-driven task system, prove_it-style.** Rejected by Rule E1 and Section 4: Go's build cache already solves the problem prove_it's task cache solves for JavaScript.

**Auto-fixing commands** (`gofmt -w`, `golangci-lint --fix`) run as the verify command. Rejected: a fixer mutates the worktree inside the commit loop, breaking the invariant that the loop's input is stable between iterations, and reproducing prove_it's own documented `resetOnFail` deadlock, where a blocking check can block the very edit that would satisfy it.

**Agent-only gating**, matching prove_it's `CLAUDECODE` check. Rejected in Section 6.

**Git notes or trailers** as a verified-commit record. Rejected in Section 7.1.

## 12. Consequences

**Positive:**
- Closes the "passes tests" gap in darna's own atomic-commit definition.
- Index-tier verification catches partial-staging, staged-deletion, and untracked-build-input failures that the static check cannot see (Section 2).
- The result cache makes symmetric gating (Rule G1) affordable: a repeated tree does not re-run the command.

**Negative:**
- Adds darna's first read-write git operations (Section 8), where all prior operations were read-only (ADR-000).
- Adds darna's first configuration file (Section 5).
- Range-tier verification cost scales with patch-set size; it is opt-in and intended for pre-push, not pre-commit, to keep it off the common path.

**Neutral:**
- The verify gate needs no package-level dependency graph. It does not depend on the shared `loadAnalysis` refactor deferred in ADR-003; that refactor remains independent future work.

## 13. Future work

This ADR sets rules for a future implementation. It does not implement the feature. Known follow-up work, out of scope here:

- `cmd/darna/main.go` has no test file today. Adding a fourth CLI mode without first making `main.go` testable would make CLAUDE.md's coverage-must-increase rule impossible to satisfy for that file. An implementation PR SHOULD extract dispatch into a testable `internal/cli` package before adding `--verify`.
- Suggested package layout for implementation: `internal/git` gains tree and worktree plumbing (`WriteTree`, `CommitTree`, `WorktreeAdd`, `WorktreeRemove`); a new `internal/worktree` package owns materialization (Rule V3); a new `internal/verify` package owns command execution (Section 4) and the result cache (Section 7), following the `(ctx, workDir) → (result, error)` shape used by `internal/validator`'s three entry points.
- MCP tool exposure for verification, alongside the MCP surface noted as unwritten future work in ADR-002 and ADR-003.
