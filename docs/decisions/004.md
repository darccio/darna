# Receiver-qualified graph symbols and the changeset-detection override

ADR-000 documents that "methods are tracked with explicit receiver notation
in the symbol ID (`pkg.Type.Method`)". The implementation did not do this:
`registerDefinitions` skipped every method and struct field (`go/types`
documents `Object.Parent()` as nil for both), and the method-ID scheme
`callerSymbolID` used for the caller side of a call never matched the plain
`pkg.Method` form `symbolID` used everywhere else. A file containing only
methods therefore contributed zero symbols to the graph — it had no edges,
so `--single-changeset` reported it as its own changeset, and
`--dependants` silently dropped any dependant whose only coupling to a base
file was a method body. **This ADR fixes the graph to match ADR-000's
documented design, and, because no fix closes the gap between "static
analysis found no dependency" and "these files are unrelated", updates
`--single-changeset`'s output to say so and adds an override.**

## Why this is a bug against documented design, not a new feature

A user reported that `--single-changeset` split a cohesive commit — a
struct, a method on it reading only its fields, and a test exercising both
— into two "independent changesets," and that committing the recommended
split produced a commit whose test failed. The reporter hypothesized the
cause was an untracked string literal (a structured-log key shared between
a source file and a test). That hypothesis was checked and rejected: no
`ast.BasicLit` handling exists anywhere in darna, so string literals really
are invisible to it, but that was not what caused this report. The coupling
was fully compiler-visible — a method's receiver type and its field reads —
and darna's graph simply was not looking at it, contradicting its own
foundational design document.

The same gap explains a second, previously unattributed report: `--dependants`
missing files whose only relationship to a base file was a method call.
`collectSymbolDependants` walks `dg.InEdges[baseSymID]` and looks up each
result in `dg.Symbols`; a method's caller ID was never a key there, so
every method-sourced dependant was silently dropped.

## Architectural decisions

| Aspect | Decision | Rationale |
|--------|----------|-----------|
| **Method IDs** | Derive `symbolID` from the `types.Object` itself, not by re-parsing the `*ast.FuncDecl`'s receiver | `callerSymbolID`'s AST-based parsing (unwrap one `*ast.StarExpr`, assert `*ast.Ident`) silently returned `""` for generic receivers (`*ast.IndexExpr`/`*ast.IndexListExpr`); the object-based approach fixes generics for free and guarantees the caller and callee sides of every call agree |
| **Struct fields** | Do **not** register fields as their own symbols; a field selection edges to the field's *owning named type* | A field is always declared in the same file as its struct — Go has no way to split them — and every consumer immediately projects `Symbols[id].File`, so an edge to `pkg.Rec` and an edge to `pkg.Rec.Baz` are equivalent at file granularity. Registering fields would need a `types.Var → owner` side table, since a field object carries no back-pointer to its struct |
| **Package-level scope guard** | `symbolID` returns `""` for anything that is neither a method nor declared in package scope (`obj.Parent() == obj.Pkg().Scope()`) | Closes the same bug class for local variables, parameters, type parameters, and imported package names shadowing a package-level identifier of the same name — e.g. a local `config :=` no longer edges to a package-level `var config` in a different file |
| **Methods depend on their receiver type** | `trackFuncBodyUsages` now inspects `fn.Recv` the same way it inspects `fn.Type` and `fn.Body` | Staging a method's file without its unstaged receiver type is a real atomicity violation darna missed; ADR-003's file-level changeset graph needs the same edge to stop treating a method-only file as isolated |
| **Changeset-split wording** | Reword `--single-changeset`'s output from "contains N independent changesets" to "appears to contain," and name what static analysis cannot see | The prior wording asserted a conclusion the tool cannot guarantee; see "Honesty of the split recommendation" below |
| **Override mechanism** | `DARNA_ALLOW_MULTI_CHANGESET=1`, an environment variable, not a new CLI flag or commit-message trailer | See the comparison table below |

## What still isn't tracked, on purpose

Registering methods and fields correctly does not chase the underlying
false-negative to zero, and this ADR does not try to:

- **Anonymous interfaces and unnamed types** have no declaration file to
  attribute a method to, so `methodSymbolID` returns `""` for them, same as
  before.
- **String literals, reflection, build tags, `go:generate` output,
  table-driven test data, and init-order effects** remain invisible. No
  symbol-graph fix can see these; see "Rejected: string-literal heuristic"
  below.

## Honesty of the split recommendation

Even with the graph fix, `--single-changeset` can still be wrong in the
direction of splitting something that should stay together — any coupling
outside `go/types`' view is by construction invisible to it. The prior
output (`cmd/darna/main.go`, before this change) stated the split as fact:

```
Commit is atomic but contains 2 independent changesets. Split into separate commits:
...
To fix, run:
   git reset
   ...
```

This gave the reader no signal that the recommendation could be wrong. The
reworded output states the limits of the analysis and offers keeping the
commit as one of two equally valid outcomes, not a fallback:

```
Commit is atomic but appears to contain 2 independent changesets.

darna found no compile-time dependency between these groups. It cannot see
runtime coupling: string keys, reflection, build tags, go:generate output,
table-driven test data, or init-order effects. If these files really belong
together, this is a false positive.

  Changeset 1:
    ...

If they are separate concerns, split them:
   git reset
   ...

If they belong together, keep the commit as is:
   DARNA_ALLOW_MULTI_CHANGESET=1 git commit ...
```

### Override mechanism: environment variable, not a flag

| Option | Per-invocation? | Needs hook edit? | Available at `pre-commit`? |
|---|---|---|---|
| `-allow-multi-changeset` flag | No | Yes | Yes |
| `DARNA_ALLOW_MULTI_CHANGESET=1` | Yes | No | Yes |
| Commit-message trailer | Yes | No | No |

A flag is set by the hook author's argv, which the committer who needs the
override cannot reach without editing an already-installed hook — at that
point it stops being a per-commit escape hatch and becomes a permanent
uninstall of the check. Their only existing recourse would be `git commit
--no-verify`, which also disables the atomicity check. `git commit` passes
its environment through to hooks, so `DARNA_ALLOW_MULTI_CHANGESET=1 git
commit -m "..."` works with every hook already installed in the wild,
without editing it.

A commit-message trailer was considered and rejected: the `pre-commit`
stage, where `--single-changeset` runs, has no commit message yet — only
`prepare-commit-msg` and `commit-msg` see one. Supporting a trailer
properly would mean shipping darna as a second hook type with its own flag
to point at the message file, a larger change than this problem warrants.

The override is never silent: when it suppresses a split, darna prints one
line to stderr naming the number of changesets it overrode, so the
suppression stays visible in hook logs.

## Rejected: `go test` per proposed sub-changeset

One remediation considered was running (or offering to run) `go test`
against each proposed changeset in isolation before recommending a split,
downgrading the recommendation to a warning when a sub-changeset fails its
own tests. Rejected:

- ADR-003 frames `--single-changeset` as a **cohesion** check — "a code
  review concern, not a build correctness one" — deliberately distinct from
  build/test correctness, which `--committable` already guarantees by
  construction for the *whole* staged set.
- darna never invokes the Go toolchain. It shells out only to `git` (read
  commands in `internal/git/git.go`) and to a user-selected LLM CLI
  (`internal/agent/agent.go`). Package loading is in-process via
  `golang.org/x/tools/go/packages` with a `map[string][]byte` overlay
  (`internal/analyzer/analyzer.go`) precisely so partially staged content
  can be analyzed without touching the working tree — `go test` cannot
  consume that overlay.
- Running each proposed changeset's tests for real would need `git worktree`
  isolation with a synthetic index, full-suite latency multiplied by the
  number of changesets inside a `pre-commit` hook, and tolerance for
  non-hermetic tests (network, cgo, containers) that would make the
  *changeset check itself* flaky.
- It would not have caught the reported bug anyway: the reporter's broken
  commit compiled and only failed a runtime assertion. Type-checking each
  proposed sub-changeset in-process (running the existing atomicity check
  against each changeset's files) is a cheap variant worth considering
  separately, but it is honestly a different, narrower guarantee than "the
  tests pass," and would not have prevented this report either.

## Rejected: string-literal heuristic linking log keys to test map indices

The reporter's second suggestion was linking a string literal used as a
structured-log key in one file to the same literal used as a map index in a
`_test.go` file elsewhere. Rejected:

- Every other signal in darna traces back to `go/types`' own symbol
  resolution. A string-literal heuristic has no ground truth: `"id"`,
  `"name"`, `"error"`, `"path"`, `"status"` recur across unrelated files in
  any real codebase. Coupling files on shared literals would collapse most
  repositories into one changeset — the same "false positives drown out the
  true case" reasoning ADR-003 already used to reject symbol-level
  changeset components.
- It has no def/use direction, so the result could only ever feed
  `DetectChangesets`; it could not inform the atomicity check or
  `--dependants`, making it a bolt-on operating on different principles
  than the rest of the tool.
- It targets one syntactic shape of runtime coupling. The same coupling
  arrives via `fmt.Sprintf` keys, exported constants, struct tags,
  `go:generate` output, and reflection; fixing one shape just relocates the
  surprise to the next one.

If author-declared coupling is ever needed for cases like this, the honest
shape is a directive the author writes, not an inference darna makes — a
`//darna:together` comment or `.darna.yml` file-group list, deterministic
and reviewable. Left as a future enhancement in ADR-003, not built here.

## Consequences

**Positive:**

- `--single-changeset` and `--dependants` now see coupling through methods
  and fields, closing the reported false positive and a previously
  unattributed `--dependants` false negative in the same fix.
- Generic methods are analyzed at all, which they were not before (the
  AST-based receiver parsing silently gave up on them).
- The implementation now matches ADR-000's documented design instead of
  silently diverging from it.
- The split recommendation is honest about what it can and cannot see, and
  a committer who has verified a staged set is atomic has a real,
  per-invocation way to say so.

**Negative:**

- Every method file is now tied to its receiver type's file for cohesion
  detection too, not just atomicity. `--single-changeset` loses some power
  to flag "two unrelated methods on the same god-object were bundled
  together." Accepted deliberately: a false-positive split produces a
  *broken commit* (the reported failure mode), while a false-negative merge
  only produces a larger one — the correct side to err on.
- The graph is denser (every method now contributes a receiver-type edge,
  every field access an owning-type edge), which widens `TransitiveDeps`
  traversals. No measured regression prompted this; if hook latency
  regresses on very large repos, a memoization layer on `TransitiveDeps` is
  a self-contained follow-up.

**Neutral:**

- `DARNA_ALLOW_MULTI_CHANGESET` is undocumented in `-h` output, matching
  every other environment-variable convention in the Go ecosystem
  (`GOFLAGS`, `NO_COLOR`); it is documented in the README instead.
